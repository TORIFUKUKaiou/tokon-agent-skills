# PR の見張り

リポジトリ全体か、指定された PR を見張る。レビューは [pr-review](../pr-review/SKILL.md) の手順で行い、報告だけをする。GitHub や Slack への書き込みは、ユーザーが指示したときだけ（pr-review の「書き込み」）。今回のユーザー指示を、このスキルより優先する。

リポジトリ全体と個別 PR のどちらも、待機と GitHub の定期確認はスクリプトに任せる。現在のチャットでバックグラウンド実行し、新しい対象・意味のある更新・実行エラーなど、対応が必要な結果を受け取ったときに処理する。

`gh` は、対象のリポジトリのアカウントになるディレクトリで実行する（組織ごとのメモ `~/.config/tokon-agent-skills/pr-review/orgs.md` があれば、それに従う）。スクリプトもそのディレクトリで動かすので、下の例の `SKILL_DIR` は、このスキルの置き場所（この SKILL.md があるフォルダ）の絶対パスに置き換える。

## 見張るもの

| 見張るもの | 使うもの | 起きたら |
|---|---|---|
| レビューの対象になった新しい PR | [scripts/wait-reviewable-pr.sh](scripts/wait-reviewable-pr.sh) | pr-review でレビューして報告する |
| 指定された PR やレビュー済み PR の動き | [scripts/wait-pr-update.sh](scripts/wait-pr-update.sh) | 下の「PR を追いかける」 |

## リポジトリを見張る

対象: open で、Draft でなく、タイトルが WIP でなく（`[WIP]`、`WIP:` など）、作者が自分でない PR。Draft が外れた PR や、タイトルから WIP が消えた PR も、その時点で対象になる。

1. 始める前に、今の対象を見せる: `bash SKILL_DIR/scripts/wait-reviewable-pr.sh OWNER/REPO --list`。すでにある PR をレビューするか、見送るかをユーザーに聞く。見送るなら `--init` で記録だけする（以後は出てこない）。
2. 待つ: `bash SKILL_DIR/scripts/wait-reviewable-pr.sh OWNER/REPO --interval 180 --timeout 36000`。新しい対象が出ると、1行1件の JSON（`number`、`title`、`author`、`url`、`headRefOid`、`baseRefName`）を出して、終了コード 0 で終わる。時間切れは 8。
   - 出した番号は `~/.local/state/pr-watch/OWNER__REPO.seen` に記録するので、同じ PR は二度出ない。やり直したいときは、その行を消す。
3. 出た PR を、1本ずつ pr-review でレビューして報告する。
4. 報告の後、すぐに 2 に戻って待ち直す。時間切れのときも、待ち直す。
5. 未承認の PR や、承認後もマージまで見るよう指定された PR は「PR を追いかける」に入れる。新規 PR の検出も並行して続ける。

## PR を追いかける

ユーザーが指定した確認間隔、終了条件、マージ前に必要な検証を控える。終了条件の指定がなければ、ユーザー自身が監視対象の PR を承認するか、PR がマージ・クローズされるまで追う。「マージまで」と指定されたら、承認後も GitHub 上のマージ完了を確認する。

開始時は `--snapshot` で比較用の値を先に取り、その後で PR の状態、base・head の SHA、本文、レビュー、インラインコメントとその返信、会話コメントを読む（取得先は pr-review の「準備」）。GitHub の情報で確認し、Slack はユーザーから監視対象に指定された場合に読む。

下の `BASELINE` には `--snapshot` または直近の待機が出力した値を渡す。`--interval` は秒単位で、省略時は900秒。

```sh
bash SKILL_DIR/scripts/wait-pr-update.sh OWNER/REPO N --snapshot
bash SKILL_DIR/scripts/wait-pr-update.sh OWNER/REPO N --since BASELINE --interval 900
```

- スクリプトはイベント受信時と定期確認時に、PR の状態・本文、CI の結果（チェックごとのワークフロー名・名前・結果。同じ結果の再実行では起きない）、レビュー、依頼中のレビュアー、コメントの ID と更新時刻を照合する。イベントは、レビューの送信、push、状態の変化、CI のチェックスイートの完了で受ける。レビューの依頼・再依頼とコメントにはイベントがないので、定期確認で拾う。CI の完了でも起きるので、push のあとは CI が終わったときにもう一度終わることがある。
- イベントで起きたのに比較結果が同じなら、API への反映を待って10秒後と40秒後に比べ直す。`gh event listen` が失敗した回は定期確認で待ち、次の回にまたイベントを試す。時間切れや同じ状態のイベントでは待機を続け、比較結果が変わったときに新しい値を1行出して終了する。
- 終了後は PR の詳細を読み、何が変わったかを確認する。更新を処理し終えたら、その待機が出力した値を次の比較に使う。読み直しの途中で入った更新も、次の待機で確認できる。取得エラーで終了した場合は、原因を確認し、最後に受け取った値から再開する。

更新が見つかったら:

| 来たもの | すること |
|---|---|
| base・head の更新 | pr-review の「再レビュー」に従って差分と前回の検証への影響を確認する |
| レビュー・返信・本文の更新 | 設計の問い、指摘への返答、検証資料や結果を確認する。head が同じ場合も、今回追加された証拠を検証する |
| 自分が投稿したレビューやコメント | 確認済みとして記録し、同じ投稿をきっかけに再レビューしない |
| ユーザー自身の Approve | 終了条件を確認する。マージまで追う場合は、未完了の検証とマージの状態を引き続き確認する |
| マージ・クローズ | GitHub の状態を読み返して監視を終了する。マージ待ちで未マージのままクローズされた場合は、その状態を報告する |
| Draft に戻った | 再レビューを保留し、個別の監視は続ける。既出の PR は新規検出スクリプトから再通知されない |

マージの監視中は、レビュー結果、GitHub 上の承認状態、残っている検証条件、マージ状態を見比べる。実機確認などの条件があれば、結果が届いたときに内容と対象 head を確認する。承認・マージの実行は pr-review の「書き込み」に従う。ユーザーから停止の指示があれば監視を終了する。

## 報告

起きたことを短く、結論から報告する。

- 新しい PR: 番号、作者、タイトル、pr-review の報告。
- 追いかけている PR: 判断に関わる変化、再レビュー結果、残っている終了条件。時間切れや変化のない確認は、定期報告の指示がある場合に報告する。
- 見張っているものの一覧（リポジトリ、PR の番号）を、聞かれたら出す。
